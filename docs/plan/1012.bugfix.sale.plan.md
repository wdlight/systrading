## 1. 개요

이 문서는 `docs/impl/1011.stock-sale.impl.md` 리뷰를 통해 발견된 **치명적인 문제점들을 해결**하기 위한 구체적인 실행 계획입니다. 현재 구현된 주식 매매 기능은 실제 매매에 사용하기에 매우 불안정하며, 금전적 손실을 유발할 수 있는 심각한 결함들을 포함하고 있습니다.

**경고: 아래의 모든 수정 작업이 완료되고, 모의투자 환경에서 완벽한 검증이 끝나기 전까지 절대로 실제 계좌를 이용한 매매를 진행해서는 안 됩니다.**

## 2. 핵심 수정 목표

1.  **데이터 신뢰성 확보**: 서버 메모리에 의존하는 임시 주문/체결 데이터 관리 방식을 버리고, **모든 데이터를 실제 한국투자증권 API를 통해 조회**하도록 변경합니다.
2.  **주문 안정성 강화**: 의도치 않은 주문(예: 지정가 -> 시장가)이 실행되지 않도록 **백엔드에 강력한 유효성 검증 로직을 추가**하고, API 호출 실패에 대비한 **안정적인 에러 처리 로직을 구현**합니다.
3.  **정확한 UI 정보 제공**: 프론트엔드에 하드코딩된 계좌 정보를 제거하고, **실시간 계좌 잔고 및 보유 수량을 연동**하여 사용자의 오판을 방지합니다.

### Phase 0: (선행 작업) `KoreaInvestAPIService` 기능 확장

**목표**: `order_service`가 호출할 수 있도록 `korea_invest.py`에 주문/체결 관련 핵심 API 연동 메서드를 미리 정의합니다.

**수정 파일**: `backend/app/core/korea_invest.py`

**수정 지침**:

1.  **`KoreaInvestAPI` 래퍼 클래스 분석**: `brokers.korea_investment.ki_api.KoreaInvestAPI`에 실제 한투 API 호출 로직이 존재한다고 가정합니다. `KoreaInvestAPIService`는 이 클래스의 비동기 래퍼 역할을 합니다.
2.  **필요 메서드 추가**: 아래 표를 참고하여 `KoreaInvestAPIService`에 신규 비동기 메서드 4개를 추가합니다. 기존 `buy_order`, `sell_order`와 유사한 패턴을 따릅니다.

| 신규 메서드명 (korea_invest.py) | 기능 | 한투 API (TR_ID) | 주요 파라미터 |
| :--- | :--- | :--- | :--- |
| `inquire_pending_orders` | 미체결 내역 조회 | **TTTC8001R** (주식/ELW/ETN 미체결) | `stock_code` (옵션) |
| `inquire_order_history` | 기간별 체결 내역 조회 | **TTTC8036R** (기간별체결내역) | `start_date`, `end_date` |
| `modify_order` | 주문 정정 | **TTTC0802U** (주식주문(정정)) | `order_number`, `new_quantity`, `new_price` |
| `cancel_order` | 주문 취소 | **TTTC0803U** (주식주문(취소)) | `order_number`, `cancel_quantity` |

**구현 예시 (`inquire_pending_orders`)**:

```python
# backend/app/core/korea_invest.py

class KoreaInvestAPIService:
    # ... 기존 코드 ...

    async def inquire_pending_orders(self, stock_code: str = "") -> Optional[Dict[str, Any]]:
        """미체결 내역 조회 (TR_ID: TTTC8001R)"""
        if not self.is_connected or not self.api_instance:
            logger.error("API가 연결되지 않았습니다.")
            return None
        try:
            # self.api_instance에 해당 동기 메서드가 구현되어 있어야 함
            result = await self._run_in_executor(
                self.api_instance.inquire_uncontracted, # ki_api.py에 구현될 메서드명 (예시)
                stock_code=stock_code
            )
            return result # APIResponse 객체 또는 dict 반환
        except Exception as e:
            logger.error(f"미체결 내역 조회 실패: {e}")
            return None

    # inquire_order_history, modify_order, cancel_order도 위와 유사하게 구현
```

### Phase 1: `OrderService` 리팩토링 및 안정성 강화

**목표**: `OrderService`의 로직을 전면 수정하여, 메모리 의존성을 제거하고 실제 API와 연동하며, 강력한 에러 처리와 명확한 응답 파싱을 구현합니다.

**수정 파일**: `backend/app/services/order_service.py`

**수정 지침**:

1.  **메모리 캐시 완전 제거**: `OrderService` 클래스에서 `_pending_orders`, `_order_history` 리스트 변수를 삭제합니다.

2.  **`get_pending_orders` 상세 구현**:
    *   Phase 0에서 만든 `inquire_pending_orders`를 호출합니다.
    *   한투 API의 응답(`output1`)을 `OrderDetail` 모델로 **명확하게 매핑**합니다.

    ```python
    # backend/app/services/order_service.py
    async def get_pending_orders(self, stock_code: Optional[str]) -> PendingOrdersResponse:
        """미체결 주문 조회 (실제 API 연동 및 파싱)"""
        try:
            api_response = await self.korea_invest.inquire_pending_orders(stock_code or "")
            if not api_response or not api_response.get('output1'):
                return PendingOrdersResponse(orders=[])

            pending_orders = []
            for item in api_response['output1']:
                order_detail = OrderDetail(
                    order_number=item.get('ord_no'),
                    stock_code=item.get('pdno'),
                    stock_name=item.get('prdt_name'),
                    order_type=item.get('ord_dvsn_cd'), # 주문구분코드
                    order_side='buy' if item.get('sll_buy_dvsn_cd') == '02' else 'sell',
                    order_status='partial' if int(item.get('tot_ccld_qty', 0)) > 0 else 'accepted',
                    quantity=int(item.get('ord_qty', 0)),
                    filled_quantity=int(item.get('tot_ccld_qty', 0)),
                    remaining_quantity=int(item.get('psbl_ord_qty', 0)), # 정정/취소가능수량
                    order_price=int(item.get('ord_unpr', 0)),
                    order_time=item.get('ord_tmd'), # 주문시각
                    # ... 기타 필요한 필드 매핑
                )
                pending_orders.append(order_detail)
            
            return PendingOrdersResponse(orders=pending_orders)
        except Exception as e:
            logger.error(f"get_pending_orders 처리 중 오류: {e}")
            raise HTTPException(status_code=500, detail="미체결 내역 조회 중 서버 오류 발생")
    ```

3.  **`place_buy_order` 상세 구현 (에러 처리 및 응답 파싱 강화)**:
    *   `buy_order`가 반환하는 `dict`가 아닌 `APIResponse` 객체(가칭)를 처리하도록 수정합니다.
    *   한투 API의 에러 코드(`rt_cd`)와 메시지(`msg1`)를 분석하여 사용자에게 명확한 피드백을 제공합니다.

    ```python
    # backend/app/services/order_service.py
    async def place_buy_order(self, request: OrderRequest) -> OrderResponse:
        """매수 주문 (유효성 검증, 응답 파싱, 에러 처리 강화)"""
        # 1. 주문 유효성 검증
        if request.order_type == OrderType.LIMIT.value and (request.price is None or request.price <= 0):
            return OrderResponse(success=False, status="rejected", message="지정가 주문은 반드시 0보다 큰 가격을 입력해야 합니다.")
        
        try:
            adjusted_price = adjust_price_to_tick(request.price) if request.order_type == OrderType.LIMIT.value else 0

            # 2. 실제 한투 API 호출
            # ki_api.py의 buy_order가 APIResponse 객체를 반환한다고 가정
            api_response_obj = await self.korea_invest.buy_order(...)
            
            # 3. APIResponse 객체 기반으로 성공/실패 처리
            if not api_response_obj.is_ok():
                # API가 에러를 반환한 경우 (rt_cd != '0')
                error_message = api_response_obj.get_message() # msg1
                logger.warning(f"매수 주문 실패: {error_message}")
                # 특정 에러 메시지에 따라 사용자 친화적 메시지로 변환 가능
                if "잔고" in error_message:
                    user_message = "증거금 또는 잔고가 부족합니다."
                else:
                    user_message = error_message
                return OrderResponse(success=False, status="rejected", message=user_message)

            # 4. 성공 응답 파싱 및 반환
            response_body = api_response_obj.get_body() # output1, output2가 포함된 객체
            order_number = response_body.output.get('ODNO')
            
            return OrderResponse(
                success=True, status="accepted", order_number=order_number,
                message="매수 주문이 정상적으로 접수되었습니다."
            )
        except Exception as e:
            logger.error(f"place_buy_order 시스템 오류: {e}", exc_info=True)
            return OrderResponse(success=False, status="rejected", message=f"시스템 오류가 발생했습니다: {e}")

    # place_sell_order, modify_order, cancel_order도 위 패턴을 적용하여 상세히 구현
    ```

# 추가 처리할 내역.

• Plan 대비 코드 상태

  - backend/app/services/order_service.py:27에 _pending_orders, _order_history가 여전히 존재하며, 주문/체결 조회는 get_pending_orders·get_order_history에서 여전
    히 이 리스트만 참고합니다. 계획서에서 요구한 “실제 한투 API 연동 + 메모리 캐시 제거”가 전혀 적용되지 않았습니다.
  - 같은 파일의 place_buy_order/place_sell_order는 응답 객체를 dict로 가정한 채 .get을 호출하고 있는데, 실제 KoreaInvestAPIService는 APIResponse 래퍼를 반환합니
    다. 계획서에는 응답 파싱 정비가 포함돼 있지만 미반영 상태라 이 함수들은 정상 주문에도 AttributeError가 발생합니다.
  - cancel_order, modify_order 역시 아직 메모리 리스트만 수정합니다. 계획서가 요구한 정정/취소 API 연동 및 원주문 조회 로직이 누락되어 있어 모의/실거래 모두 동
    작하지 않습니다.
  - backend/app/core/korea_invest.py에는 미체결·체결 조회/정정/취소용 메서드가 없는 상태입니다. 계획서가 전제한 “self.korea_invest.inquire_pending_orders()` 등
    은 존재하지 않으므로, 실제 구현 전 해당 메서드부터 설계해야 합니다.
  - 프론트엔드 stock-trading-ui/src/hooks/useOrders.ts는 order_side를 여전히 클라이언트에서 채워 보내고, 잔고/보유 수량도 하드코딩된 값(OrderForm.tsx:61)을 쓰고
    있습니다. 계획서 Phase2의 백엔드 /api/account/balance 연동 및 UI 반영이 진행되지 않았습니다.

  계획 자체의 보완점

  1. 한투 API 호출 명세: 문서가 “실제 API를 호출하라”고만 지시하고 구체적으로 어떤 TR ID를 사용할지, 응답 포맷을 어떻게 OrderDetail로 매핑할지 정의되어 있지 않
     습니다. 추후 구현자를 위해 TR 코드, 필수 파라미터, 응답 필드 매핑표를 추가하는 것이 필요합니다.
  2. 상태 저장 전략: 메모리 캐시를 걷어낼 경우에도 서버가 자체적으로 주문 상태를 추적할지(예: DB, Redis), 혹은 오직 한투 조회 결과만 신뢰할지를 명확히 해야 합니
     다. 현재 문서는 “모든 데이터를 API에서 가져오라”고만 하여, 체결 직후 조회 지연에 대한 대응 방안이 비어 있습니다.
  3. 에러 처리 플로우: KIS API는 종종 rt_cd != '0' 형태로 실패를 돌려줍니다. 계획서에 “안정적인 에러 처리”가 목표로 있으나, 구체적인 재시도/에러 메시지 전달/로
     그 정책이 없습니다.
  4. 테스트 범위: Phase 3 테스트 항목은 좋지만, 백엔드 단위 테스트 추가(예: 호가 조정·응답 파싱)나 샌드박스 토큰 만료 대비 시나리오가 빠져 있습니다. CI에서 재현
     가능한 자동 테스트 전략도 제안하면 도움이 됩니다.

  권장 후속 조치

  1. KoreaInvestAPIService에 미체결·체결 조회, 정정/취소 메서드부터 정의하고 응답 파서를 준비합니다.
  2. OrderService의 메모리 리스트 사용 부분을 전부 대체하고, APIResponse → OrderResponse 변환 로직을 명확히 작성합니다.
  3. /api/account/balance 엔드포인트를 실제 잔고 조회로 구현한 뒤, trview 페이지와 OrderForm의 availableCash/availableQuantity를 연동합니다.

  Plan이 지적한 위험 자체는 타당하지만, 현재 코드와 격차가 크고 세부 설계가 빠져 있어 추가 명세가 필요합니다.
