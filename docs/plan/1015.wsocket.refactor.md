# Domestic WebSocket `connect()` 리팩터링 계획

## 리팩터링 목표
- 단일 함수에 집중된 연결/구독/메시지 처리/백프레셔 로직을 역할 기반으로 분해하여 가독성과 유지보수성을 향상한다.
- 외부 인터페이스(`connect_with_circuit_breaker` → `connect`)와 Queue 입출력 형식을 유지해 기능적 사이드 이펙트 없이 교체 가능하도록 설계한다.
- 동시성 제어(비동기 루프, `asyncio.Event`, `asyncio.create_task`)와 백프레셔 메트릭 수집 동작을 보존하면서 테스트 가능성과 오류 대응력을 높인다.

## 현재 함수의 주요 문제점
- 200라인에 가까운 거대한 함수가 연결 준비, 구독 등록, Queue 폴링, 메시지 분기, 파싱, 백프레셔 제어를 모두 처리하여 이해와 변경이 어렵다.
- 중첩 함수(`process_queue`)가 외부 변수에 강하게 의존해 테스트가 어렵고 예외 처리도 중복된다.
- 메시지 유형별 파싱 분기가 하드코딩되어 있어 신규 TRID나 포맷 추가 시 수정 범위가 넓다.
- 로깅·메트릭·백프레셔 처리 로직이 곳곳에 흩어져 있어 장애 시 원인 파악이 어렵다.

## 타겟 아키텍처 스케치
- `DomesticWebSocketSession` (새 클래스 또는 dataclass)  
  - 소켓 연결, 공통 상태(`korea_invest_api`, `metrics_collector`, `result_monitor`, `stop_event`)를 캡슐화.
  - 진입점으로 `run()`을 노출하고, 내부에서 세부 단계 함수를 호출.
- 단계별 헬퍼
  1. `_initialize_connection(websocket)` : 초기 구독 등록 (체결 통보, 지수 구독)과 AES 키 준비.
  2. `_start_queue_consumer(websocket)` : Queue → WebSocket 구독/해제 명령을 분리하여 독립 테스트 가능하도록 개선.
  3. `_receive_messages(websocket)` : 무한 루프 본체, 메시지를 `_dispatch_message(raw)`에 위임.
  4. `_dispatch_message(raw)` : 프리픽스(`data[0]`) 기준으로 `_handle_tick`, `_handle_orderbook`, `_handle_notice`, `_handle_control` 등 세부 처리기 호출.
  5. `_push_to_result_queue(payload, *, action_id)` : 백프레셔 체크, 공통 메트릭 처리, 재시도 정책 통합.
- 메시지 파서 헬퍼
  - 기존 `receive_realtime_tick_domestic`, `receive_realtime_hoga_domestic_new`, `parse_hoga_json` 재사용.
  - 체결 통보(`receive_signing_notice`)는 필요 시 클래스 메서드화하되, 암호화 키 갱신을 `_dispatch_message`에서 관리.

## 단계별 리팩터링 로드맵

### 1차: 함수 추출 중심의 정리 (가독성 확보)
- **목표**: 초보 개발자도 흐름을 따라가기 쉬운 구조로 정리한다. 로직은 건드리지 않고 긴 블록을 의미 있는 함수로 나눈다.
- **준비 작업**
  - `connect()` 안에서 서로 다른 역할을 하는 코드 블록을 주석으로 표시해 경계선을 눈에 익힌다.
  - 새로 만들 함수가 접근해야 할 공용 데이터를 표로 정리한다(`korea_invest_api`, `websocket`, `ws_req_queue`, `ws_result_queue`, `metrics_collector`, `result_monitor`, `stop_event`, `aes_key`, `aes_iv`, `dropped_messages_count`, `last_warning_time` 등).
- **추출 대상 함수와 역할**
  1. `initialize_subscriptions(websocket, korea_invest_api)`  
     - 체결 통보 등록, 지수 구독 등록을 담당. 실패 시 예외는 상위로 전달하고, 여기서는 로깅만 수행한다.
  2. `process_queue_commands(ws_req_queue, websocket, korea_invest_api, stop_event)`  
     - 기존 중첩 함수 `process_queue`를 밖으로 꺼낸다. `asyncio.create_task(process_queue_commands(...))` 형태로 호출한다.
  3. `read_websocket_message(websocket)`  
     - `await websocket.recv()` 호출과 Timeout/ConnectionClosed 처리만 담당해 루프 본문을 단순화한다.
  4. `handle_tick_message(recv_fields, result_monitor, ws_result_queue, metrics_collector, state)`  
     - `H0STCNI0` 블록을 이동한다. `state`는 `aes_key`, `aes_iv`, 드롭 관련 카운터를 담는 dict로 정의한다.
  5. `handle_hoga_message(recv_fields, result_monitor, ws_result_queue, metrics_collector, state)`  
     - `H0STASP0` 블록을 동일하게 옮기되, JSON/파이프 분기와 백프레셔 처리를 그대로 살린다.
  6. `handle_notice_message(recv_fields, state, running_account_number, ws_result_queue)`  
     - 체결 통보(`receive_signing_notice`) 호출을 전담한다. AES 키가 없는 경우를 체크한다.
  7. `handle_index_message(body, ws_result_queue)`  
     - `H0STISE0`에서 Queue에 넣는 로직을 별도 함수로 분리한다.
  8. `handle_pingpong(message, websocket)`  
     - `PINGPONG` 메시지 수신 시 응답만 담당한다.
  9. `update_aes_state(message_body, state)`  
     - AES 키/IV를 갱신하는 코드를 한 곳으로 모은다.
  10. `push_to_result_queue(payload, action_id, result_monitor, ws_result_queue, metrics_collector, state)`  
      - 백프레셔 확인, Queue put, 메트릭 기록, 드롭 카운트 증가를 담당한다. tick/호가 처리에서 공통 사용.
- **실행 순서 예시**
  1. 위 함수들을 파일 상단 또는 `connect()` 아래에 정의하고 간단한 docstring을 작성한다.
  2. `connect()`에서 해당 블록을 잘라낸 뒤 새 함수 호출로 교체한다.
  3. 각 함수 추출 후 바로 `pytest backend/tests/...` 또는 간단한 수동 테스트로 회귀 여부를 확인한다.
- **검증 포인트**
  - Queue에 넣는 데이터 구조(`action_id`, 필드 이름)가 기존과 동일한지 확인한다.
  - 드롭 카운트, 백프레셔 로깅 등이 기존 로그와 동일하게 출력되는지 확인한다.
  - `connect_with_circuit_breaker` → `connect` 흐름이 문제없이 끝까지 실행되는지 간단한 fake Queue를 사용해 점검한다.

### 2차: 세션 클래스와 상태 캡슐화
- `DomesticWebSocketSession` 클래스를 도입해 `connect()`는 인스턴스 생성 후 `run()`만 호출하도록 단순화한다.
- `self.state`에 AES 키, 드롭 카운터 등을 모으고, Queue 소비/메시지 분배 함수를 멤버 메서드로 이동한다.
- 메시지 핸들러를 dict 매핑 형태(`{"H0STCNI0": self.handle_tick_message, ...}`)로 바꿔 신규 메시지 추가 시 코드를 최소한만 수정한다.
- Mock websocket과 Queue를 사용한 비동기 단위 테스트를 추가해 세션 단위로 검증한다.

### 3차: 구조 고도화 및 품질 강화
- 결과 Queue로 전달되는 payload를 `dataclass` 또는 Pydantic 모델로 명시해 필드 검증과 자동 문서를 지원한다.
- 백프레셔 정책, 재시도 딜레이 등을 설정 파일이나 상수 클래스로 이동해 가독성을 높인다.
- 로깅에 세션 ID, 종목 코드, 처리 지연(ms) 같은 진단 정보를 넣어 장애 분석을 쉽게 한다.
- 샌드박스 계정 + mock 데이터를 활용한 통합 테스트나 시뮬레이터를 만들어 반복 검증을 자동화한다.

## 검증 및 배포 체크리스트
- `backend/app/domestic_websocket.py`에 대한 `pytest`/통합 테스트 통과.
- 실거래 계정 대신 샌드박스 계정으로 WebSocket smoke 테스트 진행.
- 로그/메트릭 대시보드에서 새 세션 구조가 정상 표기되는지 확인.
- 장애 대응 시나리오(Queue full, 연결 끊김, 핑퐁 누락)에 대한 수동 검증 완료 후 배포.

## 예상 리스크와 대응
- **동시성 버그 도입 가능성**: 단계별 커밋과 테스트 케이스 추가로 회귀 방지.
- **외부 Queue 인터페이스 변경 위험**: 반환 payload 스키마를 리팩터링 중에 검사하고, 변경 불가 항목을 문서화.
- **실거래 환경 의존성**: 샌드박스 환경과 mock을 병행해 테스트하고, 실제 배포 전 단기 모니터링 기간 확보.
