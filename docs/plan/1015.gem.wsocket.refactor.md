# `domestic_websocket.py` 리팩터링 계획 (Gemini)

## 1. 리팩터링 목표

- **가독성 및 유지보수성 향상**: `connect()` 함수에 집중된 연결, 구독, 메시지 수신, 파싱, 분기 로직을 역할 기반의 작은 함수들로 분해하여 코드 이해도를 높입니다.
- **안전한 점진적 개선**: 외부 인터페이스(`run_websocket` 함수 및 Queue 입출력 형식)를 그대로 유지하여, 리팩터링된 코드가 기존 시스템에 부작용 없이 통합될 수 있도록 합니다.
- **테스트 용이성 확보**: 각 기능(메시지 파싱, 큐 처리 등)을 독립적인 함수로 분리하여 단위 테스트 작성을 용이하게 만듭니다.

## 2. 현재 `connect()` 함수의 문제점

- **단일 책임 원칙 위배**: 하나의 거대한 `async` 함수가 WebSocket 연결, 구독 요청 전송, 큐 폴링, 메시지 수신, 조건부 파싱, 데이터 가공, 결과 큐 전송 등 너무 많은 책임을 가지고 있습니다.
- **강한 결합**: `korea_invest_api` 객체와 큐(`ws_req_queue`, `ws_result_queue`)에 대한 의존성이 함수 전체에 흩어져 있어 코드 변경 시 수정 범위를 예측하기 어렵습니다.
- **복잡한 분기 구조**: `data[0]` 값에 따라 `0`, `1`, `JSON`으로 분기하고, 그 안에서 다시 `tr_id`로 분기하는 중첩 조건문은 새로운 메시지 유형을 추가하거나 기존 로직을 수정하기 어렵게 만듭니다.
- **상태 관리의 복잡성**: 암호화에 필요한 `aes_key`, `aes_iv`와 같은 상태 변수가 루프 내에서 관리되어 흐름을 추적하기 어렵습니다.

## 3. 리팩터링 로드맵

### 1단계: 함수 추출 (Extract Method) 중심의 최소 변경

**목표**: `connect()` 함수의 거대한 `while` 루프를 의미 있는 여러 개의 헬퍼(helper) 함수로 분리하여 가독성을 확보합니다. 이 단계에서는 로직 변경을 최소화하고 구조 개선에 집중합니다.

#### **1-1. 추출 대상 함수 정의**

1.  `_handle_request_queue(websocket, korea_invest_api, ws_req_queue)`
    - **역할**: `ws_req_queue`에서 요청을 꺼내 KIS(한국투자증권) API에 맞는 형식으로 변환 후 WebSocket으로 전송합니다.
    - **내용**: 기존 `if not ws_req_queue.empty():` 블록의 로직을 그대로 이동합니다.

2.  `_handle_realtime_data(data, ws_result_queue)`
    - **역할**: `data[0] == '0'`으로 시작하는 실시간 데이터(체결, 호가)를 파싱하고 `ws_result_queue`에 넣습니다.
    - **내용**: `if data[0] == '0':` 블록의 로직을 이동합니다. `receive_realtime_tick_domestic`, `receive_realtime_hoga_domestic` 함수를 내부에서 호출합니다.

3.  `_handle_execution_report(data, aes_key, aes_iv, account_number, ws_result_queue)`
    - **역할**: `data[0] == '1'`로 시작하는 암호화된 체결 통보를 복호화하고 `ws_result_queue`에 넣습니다.
    - **내용**: `elif data[0] == '1':` 블록의 로직을 이동합니다. `receive_signing_notice` 함수를 내부에서 호출합니다.

4.  `_handle_json_message(data, websocket)`
    - **역할**: JSON 형식의 메시지(응답, PINGPONG)를 처리합니다.
    - **내용**: `else:` 블록의 JSON 파싱 및 처리 로직을 이동합니다.
    - **반환값**: `PINGPONG` 처리, 에러 로깅 외에 `aes_key`, `aes_iv`를 반환하여 `connect` 함수의 상태를 갱신할 수 있도록 합니다.

#### **1-2. `connect()` 함수 재구성 (1단계)**

```python
async def connect(korea_invest_api, url, ws_req_queue, ws_result_queue):
    logger.info("한국투자증권 API Web Socket 연결 시도")
    running_account_number = korea_invest_api.stock_account_number
    aes_key = None
    aes_iv = None

    async with websockets.connect(url, ping_interval=None) as websocket:
        # 초기 주문 접수/체결 통보 등록
        send_data = korea_invest_api.get_send_data(cmd=5, stock_code=None)
        logger.info("[실시간 체결 통보 등록]")
        await websocket.send(send_data)

        while True:
            # 1. 요청 큐 처리
            await _handle_request_queue(websocket, korea_invest_api, ws_req_queue)

            # 2. 메시지 수신
            data = await websocket.recv()
            logger.info(f"received data: {data} \n")

            # 3. 메시지 분기 처리
            if data[0] == '0':  # 실시간 데이터 (체결, 호가)
                _handle_realtime_data(data, ws_result_queue)

            elif data[0] == '1':  # 실시간 체결 통보 (암호화)
                if not aes_key or not aes_iv:
                    logger.warning("AES key/iv가 설정되지 않아 체결 통보를 처리할 수 없습니다.")
                    continue
                _handle_execution_report(data, aes_key, aes_iv, running_account_number, ws_result_queue)

            else:  # JSON 메시지 (응답, PINGPONG)
                new_key, new_iv = await _handle_json_message(data, websocket)
                if new_key: aes_key = new_key
                if new_iv: aes_iv = new_iv
```

#### **1-3. 검증 포인트**
- 리팩터링 전/후 `ws_result_queue`에 쌓이는 데이터의 형식과 내용이 완전히 동일한지 확인합니다.
- 실시간 호가/체결 구독 및 해제 요청이 정상적으로 동작하는지 확인합니다.
- 암호화된 체결 통보가 정상적으로 복호화되어 처리되는지 확인합니다.

### 2단계: `WebSocketSession` 클래스 도입 및 상태 캡슐화

**목표**: 1단계에서 분리된 함수들과 관련 상태(`websocket`, `korea_invest_api`, `aes_key` 등)를 하나의 클래스로 묶어 관리의 편의성을 높입니다.

#### **2-1. `DomesticWebSocketSession` 클래스 설계**

- **속성(Properties)**:
  - `korea_invest_api`, `url`, `ws_req_queue`, `ws_result_queue`
  - `websocket`
  - `aes_key`, `aes_iv`, `account_number`
- **메서드(Methods)**:
  - `async run()`: `connect` 함수의 역할을 대체하는 메인 진입점.
  - `async _connect()`: WebSocket 연결 및 초기 구독 수행.
  - `async _process_messages()`: `while` 루프를 포함한 메시지 처리 로직.
  - `_handle_...` 메서드들: 1단계에서 추출한 함수들을 클래스 멤버 메서드로 전환.

#### **2-2. 메시지 핸들러 매핑**

`if/elif/else` 분기 구조를 `dict` 매핑으로 변경하여 확장성을 개선합니다.

```python
class DomesticWebSocketSession:
    def __init__(self, ...):
        # ... 속성 초기화 ...
        self.message_handlers = {
            '0': self._handle_realtime_data,
            '1': self._handle_execution_report,
        }

    async _process_messages(self):
        # ...
        handler = self.message_handlers.get(data[0])
        if handler:
            await handler(data)
        else:
            await self._handle_json_message(data)
        # ...
```

### 3단계: 구조 고도화 및 품질 강화

**목표**: 2단계에서 도입한 클래스를 기반으로 코드의 유연성과 안정성을 높입니다.

- **데이터 모델 도입**: `ws_result_queue`에 넣는 `dict`를 `dataclasses`나 `Pydantic` 모델로 정의하여 데이터의 명세와 유효성 검증을 강화합니다.
- **설정 분리**: `cmd` 값(1, 2, 3, 4, 5)이나 `tr_id` 같은 매직 넘버(magic number)를 상수나 `Enum`으로 분리하여 코드의 가독성을 높입니다.
- **로깅 개선**: 모든 로그에 세션 ID나 고유 식별자를 추가하여 여러 WebSocket 연결이 동시에 실행될 때 로그 추적을 용이하게 합니다.
- **오류 처리 강화**: `websockets.ConnectionClosed` 등 예상 가능한 예외 상황에 대한 처리 로직을 명확히 하고, 재연결 정책을 도입하는 것을 고려합니다.

## 4. 예상 리스크 및 대응 방안

- **리스크**: 1단계 함수 추출 과정에서 변수의 유효 범위(scope) 문제로 인한 버그 발생 가능성.
  - **대응**: 추출된 함수가 필요한 모든 상태(ex: `aes_key`)를 파라미터로 명시적으로 전달받도록 설계하여 의존성을 명확히 합니다.
- **리스크**: 외부 인터페이스(Queue)의 데이터 형식 변경으로 인한 사이드 이펙트.
  - **대응**: 각 단계별 리팩터링 후, 기존 시스템과 연동하여 Queue에 입력되고 출력되는 데이터가 기존과 100% 동일한지 검증하는 통합 테스트를 수행합니다.

이 계획에 따라 단계적으로 진행하면, 시스템 안정성을 해치지 않으면서도 `connect` 함수의 복잡성을 크게 낮출 수 있을 것입니다.
