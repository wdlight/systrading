## 1. 프런트엔드 요구사항 요약
- `PortfolioPerformance` 카드가 `GET /api/portfolio/history?period=<1D|1W|...>` 응답을 기대.
- 응답 포맷: `[{ date: ISO8601 string, portfolio: number, benchmark: number }, ...]`.
- 기간은 `1D`, `1W`, `1M`, `3M`, `6M`, `1Y`, `ALL`; 값은 원화 기준 누적 자산과 KOSPI 벤치마크.
- 실패 시 프런트는 mock 데이터를 사용하므로, 최소 1개 이상의 시계열 포인트를 반환해야 차트 경고(⚠️)를 제거할 수 있음.

## 2. 백엔드 인벤토리 & 활용 가능 데이터

### 2.1 계좌/포지션 (AccountService)
- `get_balance()` → `AccountBalance(summary, positions)`
  - summary: 총자산(`total_asset`), 총평가(`total_evaluation`), 총 손익(`total_profit_loss`), 수익률(`total_profit_rate`), 가용 현금 등.
  - positions: `quantity`, `avg_price`, `current_price`, `unrealized_pnl`, `profit_rate`, `day_change_rate` 등.
- 캐시(`cached_balance`, `last_update`)만 존재; 과거 snapshot 저장 없음.
- 거래 내역/입출금 기록은 미노출. `KoreaInvestAPI.get_daily_ccld()`는 일별 체결내역을 제공하나 서비스 계층에서 아직 사용하지 않음.

### 2.2 시세/차트 (TradingService + ChartCacheService)
- 종목별 **분봉/일봉** 데이터 조회 가능 (`get_minute_chart_data`, `get_day_chart_data`).
- 캐시(`kordata/<stock>/<YYYYMMDD>.json`)를 사용해 반복 호출 비용 절감.
- 일봉 생성 시 오늘 분봉을 재합성해 마지막 일봉을 보정하는 로직 존재.

### 2.3 지수 데이터 (KoreaInvestAPIService / StockInfoService)
- `get_index_current_price(market_code="U", index_code="0001")` → KOSPI 현재가, 등락률.
- 해외 지수(`get_overseas_index_price`)는 기간 조회 API를 사용하지만 국내 지수 기간 데이터용 메서드는 없음.
- `StockInfoService.get_market_indices()`는 초기 dummy/최신 값만 제공, 시계열 미구현.

### 2.4 기타 데이터 자원
- 거래 내역: `KoreaInvestAPI.get_daily_ccld` (일별 주문/체결) 활용 가능.
- 주문/체결 이력은 서비스 레벨에서 저장하지 않아 과거 포지션 SnapShot을 재구성해야 함.

## 3. 데이터 갭 정리

| 필요 데이터 | 현재 확보 여부 | 확보 방안 |
| --- | --- | --- |
| 기간별 포트폴리오 총 자산 (intraday/daily) | ❌ 단일 시점만 조회 가능 | 1) 실시간 Snapshot 스토어 구축 2) 과거 기간은 종목별 OHLC 데이터로 재계산 |
| 가용 현금/입출금 히스토리 | ❌ | `inquire-balance`에는 현재값만, 추가로 입출금 API 조사 필요. 초기 버전은 현금 고정 가정, 후속으로 개선 |
| KOSPI 벤치마크 시계열 | ⚠️ 현재가만 제공 | KIS index 차트 API 확인, 없으면 pykrx/공개 데이터로 대체 |
| 포지션 변동 이력 (거래 반영) | ❌ | `get_daily_ccld` 응답을 기반으로 필터링 후 보유량 변동 로직 작성 |
| 환율/다중 통화 지원 | ⚠️ 필요 시점 미정 | 초기에는 원화 자산 기준으로 단순화 |

## 4. 구현 계획 (Phased)

### Phase 0 — 스펙 & 모델 정비
1. **스키마 정의**: `PortfolioHistoryPoint`, `PortfolioHistoryResponse`(옵션) 추가 (`backend/app/models/schemas.py`).
2. **엔드포인트 스펙 문서화**: `docs/api` 혹은 README 섹션 업데이트.
3. **Index 코드 매핑 표 정리**: KOSPI (`U/0001`), 필요 시 KOSDAQ 등.
4. **TODO 목록**: 현금/입출금, 세금/수수료 반영 범위를 명시.

### Phase 1 — 최소 기능(MVP) 엔드포인트
1. **PortfolioAnalyticsService (신규)**  
   - 입력: 기간, 현재 포지션 목록, 차트 서비스.  
   - 처리: 기간별 타임슬롯(예: 1D→30분, 1W→일 단위) 정의 후
     - 포지션 유지 가정 하에 각 시점의 종목별 종가/분봉 종가 × 수량 합산.
     - 기존 `ChartCacheService` 재사용하여 데이터 호출 최소화.
     - 가용 현금은 현재 금액을 시계열 전체에 동일하게 반영(제한사항 명시).
   - 출력: 시계열 배열 (date ISO string, portfolio value).
2. **벤치마크**  
   - 초기: pykrx `get_index_ohlcv`로 KOSPI 종가 시계열 생성 후 직전 거래일 기준 정규화.  
   - API 호출 비용 절감 위해 파일 캐시(`data/cache/benchmarks/kospi-YYYYMMDD.json`) 도입.
3. **API 엔드포인트**: `backend/app/api/portfolio.py`
   - `/api/portfolio/history` → query param `period` 검증, `PortfolioAnalyticsService` 호출.
   - 데이터 미존재 시 204 → 프런트 fallback 유지.
4. **테스트**
   - 포지션 하나일 때와 다수일 때 합산 값 검증 (pytest + mock KIS 서비스).
   - 기간별 슬라이싱이 올바른지 확인 (예: 1W=5~7 datapoints).
5. **성능 고려**
   - Python side 계산은 holdings 수가 30 이하이면 문제없음.  
   - 결과를 Redis/파일에 TTL 캐시하여 동일 요청 반복 시 CPU 부담 감소.

### Phase 2 — 정확도 향상
1. **포지션 변동 반영**
   - `get_daily_ccld`를 일정 기간 조회 → 체결내역 기반으로 일별 보유수량 재구성.
   - Snapshot 없음 시 현재 포지션을 종단 조건으로 삼아 과거 체결을 역산.
2. **현금 흐름 추출**
   - 입출금/배당 API 조사 (`inquire-dps`, `inquire-deposit` 등 KIS 문서 확인).
   - 현금 흐름을 timeline에 반영하여 포트폴리오 총자산 정확도 개선.
3. **벤치마크 고도화**
   - KOSPI 분봉/일봉 API 직접 연동 (`inquire-time-indexchartprice` 가능 여부 확인).
   - 다중 벤치마크 (예: KOSDAQ, S&P500) 확장 대비.
4. **백테스트/시뮬레이션 모드 지원**
   - Mock 데이터 소스(예: CSV) 주입 가능하도록 인터페이스 분리.

### Phase 3 — 운영 자동화
1. **주기적 Snapshot 수집 Worker**
   - APScheduler 또는 FastAPI BackgroundTasks로 일정 간격(예: 5분)마다 `AccountService.get_balance()` 호출 → 우선 파일 캐시에 저장.
   - DB가 준비된 환경에서는 동일 파이프라인을 재사용해 `portfolio_history` 테이블에 병행 적재하도록 확장.
   - 장애 대비 롤오버 정책(일 단위 파일 분리)과 작업 중복 실행 방지 전략을 수립.
2. **알람 & 모니터링**
   - 데이터 생성 실패 시 loguru 경고 → Slack/Webhook 연동.
3. **성능/한도 관리**
   - KIS API 호출 quota 감안, 캐시 TTL 및 prefetch 전략 수립.
   - pykrx/외부 데이터 사용 시 Rate limit 고려.
4. **(선택) ORM 기반 히스토리 저장소**
   - SQLAlchemy 모델(`portfolio_history`) 및 마이그레이션 전략을 정의하고, `PortfolioAnalyticsService`가 영속 저장소를 우선 조회하도록 확장.
   - DB 세션 주입, 환경 변수, 배포 파이프라인 변경 사항을 문서화하고 검증한다.

## 5. 리스크 & 오픈 이슈
- **정확도**: 포지션을 “현재 시점 그대로” 가정하면 과거 매수/매도 영향이 반영되지 않아 왜곡 발생. Phase 2에서 체결내역 기반으로 보정 필요.
- **현금/배당 처리**: 배당 및 입출금 흐름을 반영하지 않으면 장기 기간(`6M`, `1Y`, `ALL`) 왜곡 가능.
- **인덱스 데이터 소스**: KIS가 지수 분봉을 제공하지 않으면 대체 데이터(pykrx, 증권사 API 등) 확보 필요.
- **시간대**: 모든 타임스탬프를 KST ISO (예: `2025-10-10T15:30:00+09:00`)로 정규화해야 프런트 포맷과 일치.
- **API 응답 지연**: 기간이 길수록 여러 종목의 차트를 병렬로 호출해야 하므로 asyncio.gather 활용 및 호출 실패 재시도 로직 필요.
- **운영 복잡도**: APScheduler/ORM 기반 영속 저장소를 도입할 경우 배포 파이프라인과 서비스 기동 전략이 복잡해질 수 있으므로 단계적 도입이 필요.

## 7. GEM 계획 검토 및 반영 방향

- **핵심 제안 요약**  
  `docs/plan/1010.gem.portfolio.plan.md`는 SQLAlchemy 기반 `portfolio_history` 테이블과 APScheduler 백그라운드 작업을 도입하여 주기적으로 총자산을 적재하고, `/api/portfolio/history` 엔드포인트에서 해당 데이터를 반환하는 전략을 제안합니다.

- **현행 인프라 적합성 평가**  
  현재 FastAPI 백엔드는 데이터베이스 초기화·세션 관리 모듈 없이 외부 API와 파일 캐시에 의존합니다. ORM + 스케줄러를 즉시 도입하면 환경 설정, 마이그레이션, 배포 파이프라인까지 범위가 확대되므로, Phase 1에서는 계산형/캐시형 접근을 유지하고 영속 저장소는 Phase 3 이후 심화 과제로 이관합니다.

- **반영 항목**
  1. **Phase 3 Step 1 보강**: APScheduler 또는 FastAPI BackgroundTasks를 활용한 주기적 스냅샷 수집 시나리오를 명시하고, 저장소를 “파일 캐시 → (선택) DB” 두 단계로 구분합니다.
  2. **Phase 3 신규 Step**: `portfolio_history` 테이블·ORM 모델 정의와 마이그레이션 전략을 선택 과제로 추가합니다. DB 도입 시 `PortfolioAnalyticsService`가 영속 저장소를 우선 조회하고 부족분을 계산형 파이프라인으로 보완하는 하이브리드 접근을 설계합니다.
  3. **리스크 섹션 메모**: 장기 기간(`ALL`) 계산 비용 증가와 스케줄러/영속 저장소 도입 시 배포 복잡도 상승 가능성을 명시합니다.

- **추가 검토 필요 항목**
  - 배포 환경에서 SQLite/파일 DB 사용이 가능한지, 혹은 Postgres·MySQL 등 외부 스토리지가 필요한지 사전 결정이 필요합니다.
  - APScheduler 사용 시 Uvicorn 다중 프로세스 환경에서 작업 중복 실행 방지 및 재시작 전략을 문서화해야 합니다.
  - ORM을 도입할 경우 `app/core/dependencies.py`에 세션 주입 로직을 추가해야 하므로, 서비스 전반의 DI 패턴에 대한 영향 범위를 점검해야 합니다.
