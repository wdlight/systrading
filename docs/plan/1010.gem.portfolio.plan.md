# 포트폴리오 차트 데이터 API 개발 계획 (v1.2, 2025-10-10)

## 1. 개요
프런트엔드 `PortfolioPerformanceChart` 컴포넌트에 필요한 시계열(Time-series) 데이터를 제공하는 백엔드 API 엔드포인트를 개발한다. 이 계획은 벤치마크 데이터를 포함하고, 단계별 구현 전략을 통해 리스크를 관리하며, 예상되는 주요 문제점에 대한 해결 전략을 함께 제시한다.

## 2. 현황 분석 및 요구사항 구체화

### 필요 데이터
- **포트폴리오 자산 시계열**: 일정 기간 동안의 포트폴리오 총자산 가치 변화.
- **벤치마크 시계열**: 동일 기간 KOSPI 지수 등락을 비교 기준으로 제공.
- **데이터 형태**: `[{timestamp: "YYYY-MM-DD...", portfolio_value: 12345, benchmark_value: 12300}, ...]`

### Gap 분석
- **포트폴리오 이력 부재**: 현재 시스템은 실시간 자산 스냅샷만 제공하며, 과거 이력 데이터가 없다. (**Cold Start 문제**)
- **벤치마크 이력 부재**: KOSPI 지수의 과거 시세(일봉/분봉)를 조회하는 기능이 없다.

## 3. 주요 문제점 및 해결 전략

### 문제 1: 과거 데이터 부재 및 추정치의 부정확성
- **문제점**: 기능 배포 이전의 과거 데이터가 존재하지 않아 차트가 비어 보이며(Cold Start), 이를 해결하기 위한 추정치는 실제 거래 내역을 반영하지 않아 부정확하다.
- **해결 전략**:
    1.  **데이터 유형 구분 및 시각화**: API 응답에 데이터의 종류(`type: 'actual' | 'estimated'`)를 명시하거나, 프런트엔드에서 기간에 따라 실제 데이터와 추정 데이터를 시각적으로 구분(예: 실선/점선)하여 사용자의 오해를 줄인다.
    2.  **정확도 점진적 향상 로드맵**: 초기 MVP는 추정치를 사용하되, 다음 단계에서 한국투자증권 API의 `get_daily_ccld`(일별체결내역)를 활용해 실제 거래 이력을 기반으로 과거 보유 수량을 재구성하는 방식으로 정확도를 높여나간다.

### 문제 2: 외부 벤치마크 데이터 소스 의존성
- **문제점**: 벤치마크 데이터(KOSPI)를 `pykrx` 라이브러리에 의존할 경우, 해당 서비스의 장애나 데이터 지연에 직접적인 영향을 받는다.
- **해결 전략**:
    1.  **Primary/Fallback 구조**: **(Primary)** 한국투자증권 자체 API에 지수 차트 조회 기능(`inquire-time-indexchartprice` 등)이 있는지 우선적으로 검토하고 연동한다. **(Fallback)** 공식 API가 없을 경우 `pykrx`를 예비 소스로 사용한다.
    2.  **강력한 캐싱**: 어떤 소스를 사용하든, 조회된 벤치마크 데이터는 일 단위로 파일/Redis에 캐싱하여 외부 의존도를 최소화하고 응답 속도를 확보한다.
    3.  **Graceful Degradation**: 벤치마크 데이터 조회 실패 시, API는 `benchmark_value` 필드를 `null`로 설정하여 반환한다. 프런트엔드는 이 경우 벤치마크 라인을 그리지 않도록 처리한다.

### 문제 3: 과거 데이터 추정 시 발생 가능한 성능 저하
- **문제점**: 과거 데이터 추정 로직은 보유한 모든 종목의 과거 시세를 조회하고 계산해야 하므로, 보유 종목 수가 많거나 조회 기간이 길 경우 API 응답이 지연될 수 있다.
- **해결 전략**:
    1.  **비동기 처리 및 병렬 조회**: `asyncio.gather`를 사용하여 다수 종목의 시세 조회를 병렬로 처리하여 대기 시간을 최소화한다.
    2.  **요청 단위 캐싱**: 사용자가 특정 기간(예: `1Y`)을 처음 조회했을 때, 계산된 최종 결과 JSON을 Redis에 요청 단위로 캐싱한다(예: `key: 'history:user123:1Y'`). 동일 요청 발생 시 캐시된 결과를 즉시 반환한다.
    3.  **동적 데이터 상세도 조절**: 조회 기간(`period`)에 따라 데이터의 상세도(granularity)를 동적으로 조절한다. 예를 들어, `1W`는 시간별, `1Y` 이상은 일별 종가 기준으로 계산하여 부하를 줄인다.

### 문제 4: 현금 흐름 및 배당 미반영
- **문제점**: 과거 데이터 추정 시 입출금, 배당, 수수료 등으로 인한 현금 자산의 변동을 반영하지 못해 장기 수익률 왜곡이 발생한다.
- **해결 전략**:
    1.  **한계 명시 및 점진적 개선**: 초기 버전에서는 현금 흐름이 반영되지 않는다는 점을 명확한 한계사항으로 인지하고, 다음 단계에서 관련 API(예: `inquire-dps`, `inquire-deposit`)를 조사하여 반영하는 것을 목표로 한다.

## 4. 단계별 개발 계획 (Phased Approach)

(기존 계획과 유사하나, 전략을 일부 반영)

### Phase 1: MVP - 데이터 수집 기반 구축 및 기본 API 구현
- `portfolio_history` 테이블 및 모델 정의
- **벤치마크 데이터 서비스 구현** (Primary/Fallback 및 캐싱 전략 적용)
- 주기적 데이터 수집 스케줄러(`APScheduler`) 구현
- `GET /api/portfolio/history` API 엔드포인트 개발 (수집된 실제 데이터 + 벤치마크 정규화 반환)

### Phase 2: 과거 데이터 채우기(Backfill) 및 성능 최적화
- **과거 데이터 추정 서비스 구현** (성능 전략 적용: `asyncio.gather`, 동적 상세도 조절)
- **API 로직 고도화** (실제/추정 데이터 분기 처리)
- **결과 캐싱 적용** (요청 단위 Redis 캐싱)

## 5. API 명세 (v1.2)

### `GET /api/portfolio/history`
- **Query Parameters**: `period: str` (`1D`, `7D`, `1M`, `3M`, `1Y`, `ALL`)
- **Success Response (200 OK)**:
```json
{
  "data": [
    {
      "timestamp": "2025-10-09T15:30:00+09:00",
      "portfolio_value": 10000,
      "benchmark_value": 10000,
      "type": "estimated"
    },
    {
      "timestamp": "2025-10-10T15:30:00+09:00",
      "portfolio_value": 10250,
      "benchmark_value": 10150,
      "type": "actual"
    }
  ]
}
```
