# 분봉 차트 실시간 업데이트 구현 계획 (폴링 + 캐시 하이브리드 v1.1)

## 📊 현황 요약

### 서버 측 (백엔드)
- `TradingService.get_minute_chart_data()` → `ChartCacheService.get_minute_candles()` 흐름으로 분봉 데이터를 제공.
- 캐시 구조: `kordata/{종목코드}/{YYYYMMDD}.json` 파일이 1차 캐시, 필요 시 KIS API 재호출.
- Gap-fill 로직이 `_needs_gap_fill()` 조건(현재 대비 2분 이상 지연)일 때만 API 호출을 트리거.

### 클라이언트 측 (프론트엔드)
- `useTRViewChart`에서 초기 로드시만 `/api/chart/{code}/minute` 호출.
- 실시간 갱신이 없어 새 분봉이 생겨도 수동 새로고침 필요.
- WebSocket은 호가, 체결 등 다른 기능에만 사용 중.

### 문제점
- 새 분봉 생성 직후에는 `_needs_gap_fill()`이 2분 조건이라 즉시 갱신이 되지 않음.
- 수동 새로고침 없이는 차트와 실시간 체결 정보가 어긋남.
- 폴링을 도입해도 동일 JSON을 계속 내려받아 네트워크·CPU 낭비가 발생할 수 있음.

---

## 🎯 개선 목표
1. **1분 내 반영**: 분봉이 생성된 지 최대 10~15초 내로 차트에 반영.
2. **캐시 일관성 유지**: 기존 `ChartCacheService`/`TradingService` 구조를 그대로 활용.
3. **트래픽 최소화**: 중복 호출, 불필요한 전체 데이터 재전송을 줄이는 보조 전략 마련.
4. **초보 개발자도 이해 가능한 가이드**: 단계별로 명확한 TODO와 코드 위치 안내.

---

## 🧱 전체 아키텍처 개요

```
[KIS API] ←→ [KoreaInvestAPIService]
                ↓
          [ChartCacheService]
                ↓
         [TradingService API]
                ↓
      [Next.js Chart Hooks + 폴링]
```

### 핵심 아이디어
- **폴링으로 새 데이터 확인**: 5초 주기로 REST API를 호출하되, 요청/응답을 가볍게 만들기 위한 장치 추가.
- **Gap-fill 조건 완화**: `_needs_gap_fill()`을 2분 → 15초 전후로 조정하여 새 분봉을 빠르게 캐시에 반영.
- **체결 이벤트 활용(선택)**: WebSocket 틱 수신 시 캐시 최신화 플래그를 세팅해 폴링 직전에 강제 리프레시.
- **프론트 락 & 백오프**: 요청 중복을 피하고 에러 시 폴링 간격을 자동으로 늘렸다가 정상화되면 복귀.

## 🚀 구현 단계 (초보 개발자용 상세 가이드)

### Phase 1. 백엔드 캐시 갱신 로직 강화

#### 1-1. `_needs_gap_fill` 조건 조정
- **파일**: `backend/app/services/chart_cache_service.py`
- **함수**: `_needs_gap_fill`
- **작업**:
  1. 기존 `2분` 임계값을 `15~20초`로 낮춤.
  2. Gap 판단 시 `TradingHoursManager.is_regular_hours` 조건을 그대로 활용하되, 장외 시간에는 불필요한 호출을 피함.
  3. 주석으로 “실시간 폴링 대응을 위해 Gap 허용 시간을 줄입니다” 라는 설명 추가.
  4. 테스트: 장중 더미 데이터를 넣고 마지막 타임스탬프와 현재 시간 차이를 바꿔가며 함수가 True/False를 올바르게 반환하는지 확인.

```python
# 예시 코드 조각
gap_seconds = (now - latest_time).total_seconds()
gap_minutes = gap_seconds / 60

# 기존: if gap_minutes >= 2:
if gap_seconds >= 15:
    logger.info("Gap detected ...")
    return True
```

#### 1-2. WebSocket 체결 이벤트로 갱신 플래그 세팅 (선택)
- **파일**: `backend/app/services/realtime_service.py`
- **함수**: `_handle_tick_data`
- **작업**:
  1. `self._minute_cache_dirty: Dict[str, datetime]` 같은 딕셔너리를 서비스 초기화 시 추가.
  2. 체결 데이터를 받으면 해당 종목 코드에 현재 시간을 기록 (`self._minute_cache_dirty[stock_code] = datetime.now()`).
  3. `ChartCacheService.get_minute_candles` 호출 직전, 이 딕셔너리를 확인하여 “최근 5초 내 체결이 있었으면 강제로 Gap-fill 로직 실행” 같은 처리.
  4. 구현이 부담스럽다면 주석으로 “차후 확장”이라고 명시하고, 현재 리비전에서는 Gap 완화만 먼저 적용.

### Phase 2. API 응답 최적화

#### 2-1. ETag 또는 타임스탬프 비교 도입
- **파일**: `backend/app/api/chart.py`
- **엔드포인트**: `/api/chart/{stock_code}/minute`
- **작업**:
  1. 응답에 `last_updated` 필드를 추가 (`최신 캔들의 timestamp` 사용).
  2. 요청 시 `?since=ISO8601` 같은 쿼리를 받아, 서버에서 최신 데이터의 timestamp가 `since`보다 같거나 오래되면 빈 배열/“갱신 없음” 메시지를 내려줌.
  3. 초보자 가이드: “프론트에서 이전에 받은 마지막 캔들 timestamp를 기억해서 재사용한다”라고 주석/문서에 명시.
  4. 추후 네트워크 최적화를 위해 ETag도 고려할 수 있으나 v1.1에서는 timestamp 비교로 충분.

```python
last_timestamp = candles[-1].timestamp if candles else None
return {
    "success": True,
    "data": serialized_candles if is_newer else [],
    "last_updated": last_timestamp,
    "is_incremental": not is_newer
}
```

#### 2-2. 메모리 캐시 유지
- Phase 1에서 언급한 메모리 캐시는 여전히 유효. TTL은 5초 유지.
- 메모리 캐시 키 구조: `f"{stock_code}_{date}"`.
- 캐시 히트 시 `logger.debug`로 체크하여 확인 가능.

### Phase 3. 프론트엔드 폴링 & 동기화

#### 3-1. 폴링 헬퍼 구현
- **파일**: `stock-trading-ui/src/hooks/useTRViewChart.ts`
- **작업**:
  1. `useRef`로 `isFetching` 플래그를 두어 요청 중복 방지.
  2. `fetchData({ silent: true })` 호출 전 플래그 체크, 완료 후 해제.
  3. 연속 실패 횟수를 카운트하여 3회 이상 실패 시 폴링 간격을 2배씩 늘리는 간단한 backoff 구현.
  4. 정상 응답이 돌아오면 간격을 원래대로 복원하고 콘솔에 “폴링 간격 복구” 메시지를 남김.

```typescript
if (isFetchingRef.current) {
  return; // 이미 요청 중이면 스킵
}

isFetchingRef.current = true;
try {
  await fetchData({ silent: true, since: lastTimestampRef.current });
  failureCountRef.current = 0;
} catch (err) {
  failureCountRef.current += 1;
} finally {
  isFetchingRef.current = false;
}
```

#### 3-2. 마지막 타임스탬프 관리
- `fetchData` 결과에서 최신 캔들의 `timestamp`를 `lastTimestampRef.current`에 저장.
- 다음 폴링 시 `chartAPI.getMinuteCandles(stockCode, { since: lastTimestamp })` 형태로 전달.
- 서버가 “갱신 없음”을 반환하면 `setChartData`를 호출하지 않고 로그만 남김.

#### 3-3. 탭 가시성 이벤트
- 기존 문서에 있던 `document.visibilitychange` 예제 적용.
- 백그라운드로 가면 폴링 타이머 중단, 복귀 시 즉시 한 번 호출 + 타이머 재시작.
- 초보 개발자를 위한 팁: 주석으로 “브라우저가 백그라운드 탭은 타이머를 자동으로 늦출 수 있으니, 직접 stop/start로 관리합니다.”라고 적기.

### Phase 4. 검증 & 모니터링

#### 4-1. 로그 체크
- `ChartCacheService`: Gap-fill 실행 여부, 메모리 캐시 히트율 로그 확인.
- `realtime_service`: 캐시 더티 플래그가 의도대로 작동하는지 `logger.debug`로 추적.

#### 4-2. 수동 테스트 시나리오
1. 장 중 실시간 데이터를 모사하기 어렵다면, JSON 파일의 마지막 캔들 timestamp를 수동으로 과거로 변경하고 API 호출이 재실행되는지 확인.
2. 프론트 폴링이 `lastTimestamp`를 제대로 전달하는지 DevTools Network 패널로 확인.
3. 브라우저 탭을 숨겼다 나타나며 폴링이 멈췄다가 재개되는지 Console 로그로 확인.

#### 4-3. 향후 측정 포인트
- API 호출 횟수/분, 평균 응답 시간, “갱신 없음” 응답 비율 → Prometheus/Grafana에 붙일 여지.
- 사용자 체감 지연 시간: 장중 테스트가 가능하다면 체결 후 몇 초 뒤 차트에 반영되는지 측정.

## ✅ 마무리 체크리스트
- [ ] `_needs_gap_fill`이 15초 기준으로 동작하는지 로그로 확인했다.
- [ ] `/api/chart/{code}/minute` 응답에 `last_updated`가 포함되고, 프론트에서 전달한 `since`보다 최신인 경우에만 데이터가 내려온다.
- [ ] 폴링 타이머가 중복으로 돌아가지 않도록 `isFetchingRef`를 추가했다.
- [ ] 네트워크 오류가 3회 연속 발생하면 폴링 간격이 두 배로 늘어나며, 정상 응답 후 원래 간격으로 복구된다.
- [ ] 탭을 숨기면 폴링이 중단되고, 다시 보이면 즉시 한 번 호출되며 타이머가 재시작된다.
- [ ] (선택) 체결 WebSocket을 활용해 캐시 더티 플래그를 세팅하는 코드를 추가했다.

> 위 체크리스트를 순서대로 확인하면, 초보 개발자도 기존 시스템 구조를 크게 건드리지 않고 실시간에 가까운 분봉 업데이트를 구현할 수 있습니다.
