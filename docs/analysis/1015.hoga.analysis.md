# 2025-10-15 호가 실시간 갱신 분석 보고서

본 문서는 2025년 10월 15일 진행된 호가(order book) 실시간 갱신 문제에 대한 점검 결과를 정리한 자료입니다. 초보 개발자도 전체 구조를 이해하고 후속 조치를 수행할 수 있도록 최대한 상세하게 설명합니다.

---

## 1. 전체 구성 요약

### 1-1. 백엔드 구성
- `FastAPI` 앱(`backend/app/main.py`)이 기동되면 lifespan 훅에서 다음을 수행합니다.
  - `KoreaInvestAPIService` 초기화 (한국투자증권 API 인증 및 래퍼)
  - 실시간 용도 큐 2개 준비
    - `ws_req_queue`: 실시간 구독/해제 요청을 담는 큐 (최대 500개)
    - `ws_result_queue`: 실시간 데이터 결과를 담는 큐 (최대 2000개)
  - 실시간 처리 서비스 `RealtimeDataService` 시작
  - 별도 프로세스로 `domestic_websocket.run_websocket(...)` 실행
  - 큐 상태 감시, 성능 메트릭 수집, 스케줄러 기동

### 1-2. KIS WebSocket 프로세스(`backend/app/domestic_websocket.py`)
- 한국투자증권 WebSocket 서버와 실제 연결을 담당하는 자식 프로세스.
- `ws_req_queue`에서 요청을 하나씩 꺼내 실시간 구독/해제 메시지를 한국투자 측으로 전송.
- 수신 데이터는 `ws_result_queue`에 구조화된 JSON 형태로 넣어줌.
- 핵심 데이터 타입
  - 체결(TICK): `action_id='실시간체결'`
  - 호가(ORDER BOOK): `action_id='실시간호가'`
- 파싱 로직
  - 호가 데이터는 `^`로 구분된 문자열 포맷(`H0STASP0`)을 파싱해 10호가까지 변환.
  - 파싱 결과를 큐에 넣기 전에 모니터링 및 백프레셔(가득 찼을 때 잠시 대기) 처리.

### 1-3. 실시간 서비스(`backend/app/services/realtime_service.py`)
- `RealtimeDataService`가 백엔드 메인 프로세스에서 동작.
- 주기적으로 `ws_result_queue`에서 메시지를 꺼내 배치 처리.
- `action_id`별 핸들러에서 다음 역할 수행:
  - 호가 데이터: 캐시에 저장하고, 구독 중인 클라이언트에게만 전송.
  - 체결 데이터: 별도 로직(미작성 부분)에서 활용 예정.
- 호가 데이터 전송은 `ConnectionManager.broadcast_to_stock_subscribers()`를 통해 특정 종목을 듣고 있는 WebSocket 클라이언트에게만 전달.
- 거래시간 검사(`TradingHoursManager.is_trading_hours`) 후 장이 열려 있을 때만 호가 데이터를 유효하게 처리.

### 1-4. 프론트엔드 흐름
- `stock-trading-ui/src/hooks/useOrderBook.ts`
  - 페이지 진입 시 REST API(`/api/realtime/orderbook/{stock_code}`)로 초기 스냅샷 요청.
  - `subscribe()` 호출 시
    1. 백엔드 REST 엔드포인트(`/api/realtime/subscribe/orderbook`)에 POST 요청 → 백엔드 `ws_req_queue`에 등록 요청이 들어감.
    2. 이미 연결된 WebSocket(`wsManager`)이 있다면 `{"type":"subscribe","stock_code":...}` 메시지를 `/ws`로 전송 → 백엔드 ConnectionManager가 해당 클라이언트를 종목 구독자로 등록.
  - `subscribeToOrderBookUpdates(...)`를 통해 `orderbook_update` 타입 메시지를 구독하고 UI 상태를 갱신.
- `stock-trading-ui/src/lib/websocket.ts`
  - `/ws` 소켓과 연결을 관리.
  - 서버에서 전달된 메시지를 타입별로 리스너에게 배포.
  - 재연결, 하트비트, 로그 샘플링 등 부가 기능 포함.

## 2. 오늘 관측한 문제와 원인 추정

### 2-1. `Queue.empty()` 사용으로 인한 요청 정체 가능성
- `domestic_websocket`와 `RealtimeDataService` 모두 큐를 사용할 때 `queue.empty()`를 먼저 검사한 뒤 `get_nowait()`로 꺼내고 있음.
- 파이썬 공식 문서에 따르면 `empty()`는 멀티프로세스 환경에서 신뢰할 수 없음.
  - 다른 프로세스가 큐에 항목을 넣었더라도 `empty()`가 `True`를 반환할 수 있음.
  - 이 경우 실제로는 데이터가 있는데도 루프가 데이터가 없다고 판단하고 다음 반복으로 넘어가거나, sleep으로 빠져나와 처리 지연이 발생.
- 실제 현상: `/api/realtime/debug/queue-status`에서 `ws_req_queue_size`가 4처럼 증가하지만 소비되지 않는 문제가 보고됨.
- 해결 방향: `empty()` 사용을 피하고, `try: queue.get_nowait()` + `except Empty` 패턴으로 전환해야 함.

### 2-2. WebSocket 구독 메시지 누락 가능성
- `useOrderBook.subscribe()`는 REST 구독 요청 성공 여부만 보고 `isSubscribed`를 바로 `true`로 바꿈.
- `wsManager.isConnected()`가 `false`인 상태에서 `subscribe`가 호출되면 `/ws`로 실제 구독 메시지가 전달되지 않음.
  - 백엔드는 종목 구독자가 없는 것으로 판단하여 `broadcast_to_stock_subscribers`에서 아무도 없는 상태로 메시지를 버림.
- 초기 접속 시점에 WebSocket 연결이 아직 완료되지 않았다면 구독 메시지가 누락될 가능성이 큼.
- 해결 방향
  - WebSocket 연결이 열린 뒤 REST 요청을 보내도록 순서를 보장하거나,
  - 연결이 열릴 때 미처 보낸 적이 없는 구독 요청을 재전송하는 버퍼링 로직을 추가.

### 2-3. 거래시간 체크 로직에 따른 데이터 필터링
- `RealtimeDataService._handle_hoga_data()`는 `TradingHoursManager.is_trading_hours(datetime.now())`가 `False`면 데이터를 무시.
- 장이 닫힌 시간(예: 저녁, 새벽)에 테스트하면 데이터가 수신되더라도 캐시에 저장되지 않고 브로드캐스트도 일어나지 않음.
- 로컬에서 테스트할 때는 실제 장 시간과 맞춰 확인하거나, 진짜 운영 시간 외에 테스트하려면 임시로 이 검사를 우회해야 함.

### 2-4. 단독 실행 스크립트 매개변수 불일치
- 파일 하단 `if __name__ == "__main__":` 블록에서 `run_websocket`을 호출할 때 `korea_invest_service.api_instance`를 전달.
- 하지만 현재 `run_websocket` 정의는 `(settings, ws_url, ws_req_queue, ws_result_queue)`를 기대.
- 따라서 단독 실행 시 에러가 발생하고 WebSocket 연결이 시작되지 않음.
- 해결 방향: 단독 실행 경로가 실제로 필요하다면 시그니처를 맞추거나, 필요 없다면 명시적으로 예외를 던져 개발자가 혼동하지 않게 조치.

## 3. 점검 및 재현 방법

1. **백엔드 기동**
   ```bash
   cd backend
   ./vkis/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
   ```
   - 로그에 `domestic_websocket 프로세스를 시작했습니다`가 나오는지 확인.

2. **큐 상태 확인**
   ```bash
   curl http://localhost:8000/api/realtime/debug/queue-status
   ```
   - `ws_req_queue_size`가 구독 요청 후 감소하는지 체크.
   - 증가만 하고 감소하지 않으면 큐 소비가 막힌 것.

3. **호가 구독 API 호출**
   ```bash
   curl -X POST "http://localhost:8000/api/realtime/subscribe/orderbook?stock_code=005930"
   ```
   - 성공 시 `"종목 005930 호가 구독 시작"` 응답.
   - 동시에 백엔드 로그에 `[DEBUG] 호가 구독 데이터 전송` 메시지가 찍혀야 함.

4. **WebSocket 메시지 흐름 확인**
   - 프론트엔드에서 `/ws` 연결이 열렸는지 브라우저 콘솔에서 확인 (`WebSocket 연결됨` 로그 등).
   - 구독 메시지(`{"type":"subscribe","stock_code":"005930"}`)가 전송되는지 Network 탭의 WebSocket 프레임에서 확인.
   - 백엔드 `ConnectionManager` 로그에서 `종목 구독: 005930`가 나오는지 확인.

5. **호가 데이터 수신 확인**
   - 장시간일 때 `RealtimeDataService` 로그에 `📊 호가 데이터 처리`, `📡 호가 데이터 브로드캐스트` 메시지가 주기적으로 나타나야 함.
   - 프론트엔드 콘솔에는 `📊 호가 데이터 업데이트` 로그로 데이터가 표시.
   - REST로도 캐시 확인 가능:
     ```bash
      curl http://localhost:8000/api/realtime/orderbook/005930
     ```
   - 캐시가 잘 채워졌다면 `current_price`와 10개 ask/bid가 0이 아닌 값으로 내려옴.

## 4. 개선 계획 (Action Plan)

1. **큐 처리 안정화**
   - `domestic_websocket`와 `RealtimeDataService`에서 `queue.empty()` 사용을 제거.
   - 다음 패턴으로 수정:
     ```python
     try:
         req_data = ws_req_queue.get_nowait()
     except queue.Empty:
         await asyncio.sleep(0.01)
         continue
     ```
   - 후속으로 `ws_req_queue_size`가 정상적으로 줄어드는지 다시 확인.

2. **프론트엔드 구독 순서 정비**
   - `wsManager.connect()` 완료(readyState OPEN) 후 REST 구독을 요청하도록 순서를 보장.
   - 연결 대기 중일 때는 임시 큐에 종목을 저장했다가 `onopen` 이벤트에서 한번에 subscribe 메시지를 보내는 구조도 고려.
   - `isSubscribed` 상태를 WebSocket 등록까지 확인한 뒤에만 `true`로 변경.

3. **거래시간 검사 유연화**
   - 개발/테스트 모드에서는 `TradingHoursManager` 체크를 옵션으로 끌 수 있도록 환경 변수를 도입.
   - 예: `KI_SKIP_TRADING_HOURS_CHECK=true`이면 항상 데이터를 저장하도록 처리.
   - 운영에서는 그대로 유지해 불필요한 야간 데이터가 쌓이지 않도록 함.

4. **단독 실행 경로 정리**
   - 필요 시 `run_websocket(settings, ...)` 호출로 수정하거나,
   - "이 모듈은 FastAPI 프로세스에서만 실행하세요"라는 예외를 던져 개발자가 잘못 실행하지 않도록 안내.

5. **로그 정리 및 문서화**
   - 현재 로그는 디버깅 용도로 매우 상세함. 문제 해결 후에는 로그 레벨을 낮추거나 샘플링 비율을 조정해 운영 시 과도한 로그가 쌓이지 않도록 할 것.
   - 본 문서를 `docs/analysis/1015.hoga.analysis.md`로 보관했고, 후속 조치 내역은 `docs/work-log`나 `docs/plan`에 추가 기록.

## 5. 초보 개발자를 위한 핵심 요약

- **두 개의 큐가 핵심**  
  - `ws_req_queue`: 구독/해제 요청 송신용  
  - `ws_result_queue`: 실시간 데이터 수신용  
  이 큐가 막히면 전체 흐름이 끊기므로 큐 상태를 늘 확인해야 함.

- **프론트엔드 WebSocket 연결이 꼭 필요**  
  - REST 구독만 성공해도 실시간 데이터가 반영되지 않을 수 있음.  
  - WebSocket이 연결되고 `subscribe` 메시지를 보내야 비로소 데이터를 받을 수 있음.

- **테스트 시간도 중요**  
  - 장이 닫힌 시간에는 의도적으로 데이터를 버리도록 설계되어 있음.  
  - 테스트는 가능한 장 시간(09:00~15:30)에 맞추거나 임시로 검사 로직을 비활성화해야 함.

- **로그와 도구 활용**  
  - `/api/realtime/debug/queue-status`: 큐 상태 빠르게 확인  
  - `/api/realtime/get_cache_status`: 캐시된 호가 데이터 확인 가능  
  - 브라우저 콘솔/Network 탭에서 WebSocket 프레임을 직접 살펴보면 많은 힌트를 얻을 수 있음.
