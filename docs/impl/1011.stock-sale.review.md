## 핵심 이슈 요약

1. **시장가 주문 거부/잘못된 주문 전송 (Critical)**  
   - 근거: `backend/app/models/order_models.py:53`, `backend/app/services/order_service.py:52`, `backend/app/services/order_service.py:146`  
   - 원인: `OrderRequest`가 `Config.use_enum_values = True`로 인해 `order_type`을 문자열로 보관하는데, validator와 서비스는 `OrderType.MARKET` Enum과 직접 비교하고 있음.  
   - 영향: 시장가 주문이 422로 거부되거나, 임시로 가격을 채워 넣더라도 호가 조정 로직이 실행되어 잘못된 가격이 KIS API로 전송됨. 실제 매매 시 즉시 체결 예상인 주문이 지정가 주문으로 바뀌어 체결 실패/오류 가능.

2. **주문 상태 관리 불가 (Critical)**  
   - 근거: `backend/app/api/orders.py:26`, `backend/app/services/order_service.py:29`  
   - 원인: FastAPI 의존성에서 요청마다 `OrderService` 새 인스턴스를 생성. 서비스 내부의 `_pending_orders`, `_order_history` 캐시는 항상 빈 상태.  
   - 영향: `/api/orders/pending` 및 `/api/orders/history`는 항상 빈 리스트를 반환하며, 정정/취소 API는 대상 주문을 찾을 수 없음. 프론트엔드 `OrdersList`는 계속 “미체결 없음”만 표시.

3. **buy/sell API 계약 불일치 (Medium)**  
   - 근거: `backend/app/models/order_models.py:37`, `backend/app/api/orders.py:40`  
   - 원인: `OrderRequest.order_side`가 필수 필드이나, 엔드포인트는 내부에서 값을 덮어씀.  
   - 영향: 클라이언트가 `order_side` 없이 요청하면 FastAPI가 422를 반환. 엔드포인트 의도(매수/매도 분리)와 맞지 않아 호출자가 혼란을 겪을 수 있음.

## 추가 관찰 / 권장 조치

- `docs/plan/1011.stock-sale.plan.md`와 `docs/execution/1011.stock-sale.impl.md`는 실서비스 연동을 전제로 하고 있으나, 현재 구현은 메모리 캐시에 의존함. 정식 배포 전 `KoreaInvestAPIService` 기반의 실제 조회/정정/취소 로직을 반드시 연결할 것.
- 프론트엔드 `OrderForm`은 `price`를 0으로 보내 시장가 주문을 기대하지만, 현재 백엔드 문제로 인해 동작하지 않음. 백엔드 수정 후에도 end-to-end 검증 필요.
- `OrderService`는 asyncio 환경에서 상태 공유 시 동시성 문제가 발생할 수 있으므로, 싱글톤 주입 또는 외부 저장소(예: Redis/DB)로 이전하는 방향을 고려.

## 대응 우선순위 제안

1. **시장가 비교 로직 수정**: `OrderRequest` validator와 `OrderService`에서 Enum 대신 `.value` 비교 또는 `use_enum_values` 제거. 시장가 주문 시 `order_price=0`이 그대로 전달되도록 보장.  
2. **OrderService 스코프 재조정**: FastAPI 의존성을 싱글톤으로 바꾸거나, 상태를 외부 저장소로 이동. 임시 캐시라면 실제 구현 전까지는 API에서 명시적으로 “미구현” 오류를 반환하도록 조정.  
3. **요청 스키마 정리**: `/buy`와 `/sell`에서 `order_side`를 선택적 필드로 변경하거나, 엔드포인트별 전용 Pydantic 모델을 분리하여 422를 방지.

## 🔧 수정 완료 내역 (2025-10-12)

### Issue 1: 시장가 주문 거부 문제 ✅ 해결

**문제점**: `use_enum_values = True`로 인해 Enum 비교가 작동하지 않음

**수정 파일**:
1. `backend/app/models/order_models.py:58`
   - 변경 전: `if order_type == OrderType.MARKET:`
   - 변경 후: `if order_type == OrderType.MARKET.value:`

2. `backend/app/services/order_service.py:53`
   - 변경 전: `if request.order_type != OrderType.MARKET and request.price:`
   - 변경 후: `if request.order_type != OrderType.MARKET.value and request.price:`

3. `backend/app/services/order_service.py:147`
   - 매도 주문에서도 동일하게 `.value` 사용

**결과**: 시장가 주문 시 `order_price=0`이 정상적으로 KIS API로 전달됨

### Issue 2: 주문 상태 관리 불가 ✅ 해결

**문제점**: FastAPI 의존성에서 매번 새 인스턴스 생성으로 캐시 항상 빈 상태

**수정 파일**: `backend/app/api/orders.py:26-37`

**수정 내용**:
```python
# 싱글톤 패턴 적용
_order_service_instance: Optional[OrderService] = None

def get_order_service(
    korea_invest_service: KoreaInvestAPIService = Depends(get_korea_invest_service)
) -> OrderService:
    """주문 서비스 의존성 주입 (싱글톤 패턴)"""
    global _order_service_instance
    if _order_service_instance is None:
        _order_service_instance = OrderService(korea_invest_service)
    return _order_service_instance
```

**결과**:
- `/api/orders/pending` 및 `/api/orders/history`가 정상적으로 주문 목록 반환
- 주문 정정/취소 시 대상 주문을 찾을 수 있음

### Issue 3: buy/sell API 계약 불일치 ✅ 해결

**문제점**: `OrderRequest.order_side`가 필수 필드이나 엔드포인트가 덮어씀

**수정 파일**: `backend/app/models/order_models.py:42`

**수정 내용**:
```python
# 변경 전
order_side: OrderSide = Field(..., description="매수/매도 구분")

# 변경 후
order_side: Optional[OrderSide] = Field(None, description="매수/매도 구분 (엔드포인트에서 자동 설정)")
```

**결과**:
- 클라이언트가 `order_side` 없이 요청 가능
- `/buy`와 `/sell` 엔드포인트가 자동으로 설정
- 422 에러 발생하지 않음
