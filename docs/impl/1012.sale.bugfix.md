## 2. 백엔드 수정 내역 (`backend/`)

### 2.1. `app/core/korea_invest.py` - API 서비스 계층 확장

**목표**: `OrderService`가 주문/체결 관련 모든 기능을 API를 통해 처리할 수 있도록 `KoreaInvestAPIService`에 핵심 메서드를 추가하고 기존 메서드를 개선했습니다.

**주요 변경 사항**:

1.  **`buy_order`, `sell_order` 메서드 수정**:
    *   기존에는 주문 성공 시 단순 `dict`를 반환했으나, 이제 한투 API의 응답을 그대로 담은 `APIResponse` 객체를 직접 반환하도록 변경했습니다.
    *   이를 통해 서비스 레이어에서 `rt_cd`, `msg1` 등 API의 상세한 응답을 직접 처리할 수 있게 되었습니다.

    ```python
    # 수정 후 buy_order 예시
    async def buy_order(self, stock_code: str, order_qty: int, order_price: int, order_type: str = "00") -> Optional[Any]:
        """매수 주문 (비동기) - APIResponse 객체를 직접 반환하도록 수정"""
        # ...
        try:
            api_response = await self._run_in_executor(
                self.api_instance.buy_order, 
                stock_code, order_qty, order_price, order_type
            )
            return api_response
        # ...
    ```

2.  **신규 API 연동 메서드 4종 추가**:
    *   계획에 따라 미체결 조회, 체결 내역 조회, 주문 정정/취소를 위한 비동기 메서드를 추가했습니다.

    | 신규 메서드명 | 기능 | 호출 대상 (ki_api.py) |
    | :--- | :--- | :--- |
    | `inquire_pending_orders` | 미체결 내역 조회 | `inquire_uncontracted` |
    | `inquire_order_history` | 기간별 체결 내역 조회 | `inquire_history` |
    | `modify_order` | 주문 정정 | `modify_order` |
    | `cancel_order` | 주문 취소 | `cancel_order` |

### 2.2. `app/services/order_service.py` - 서비스 로직 전면 리팩토링

**목표**: 인메모리(in-memory) 데이터 의존성을 완전히 제거하고, 모든 주문 관련 로직이 `KoreaInvestAPIService`를 통해 실제 API와 통신하도록 전면 재작성했습니다.

**주요 변경 사항**:

1.  **메모리 캐시 제거**: `__init__`에서 `self._pending_orders`와 `self._order_history` 리스트를 삭제하여 상태 비저장(stateless) 서비스로 전환했습니다.

2.  **주문 실행 메서드 (`place_buy_order`, `place_sell_order`) 개선**:
    *   `korea_invest.py`에서 반환된 `APIResponse` 객체를 직접 처리합니다.
    *   `api_response_obj.is_ok()`를 통해 API 호출의 성공/실패를 명확히 분기합니다.
    *   실패 시 `get_message()`로 사용자 친화적인 에러 메시지(예: "증거금 또는 잔고가 부족합니다.")를 생성하여 반환합니다.
    *   지정가 주문 시 가격이 0 이하인 경우 API를 호출하기 전에 즉시 거부하는 유효성 검증 로직을 추가했습니다.

3.  **주문 조회 메서드 (`get_pending_orders`, `get_order_history`) 구현**:
    *   `get_pending_orders`는 `korea_invest.inquire_pending_orders`를 호출하고, API 응답의 `output1`을 파싱하여 `OrderDetail` 리스트로 변환 후 반환합니다.
    *   `get_order_history` 역시 `korea_invest.inquire_order_history`를 호출하여 동일한 방식으로 체결 내역을 반환합니다.

4.  **주문 정정/취소 메서드 (`modify_order`, `cancel_order`) 구현**:
    *   인메모리 리스트를 수정하는 대신, `korea_invest.modify_order`와 `korea_invest.cancel_order`를 호출하여 실제 API로 정정/취소 요청을 보내도록 수정했습니다.

### 2.3. `tests/test_order_service.py` - 단위 테스트 추가

**목표**: 코드 안정성 확보를 위해 `OrderService`에 대한 단위 테스트를 추가했습니다.

**주요 변경 사항**:

1.  **테스트 파일 생성**: `backend/tests/test_order_service.py` 파일을 신규 생성했습니다.
2.  **유효성 검증 테스트 추가**: 지정가 주문 시 가격이 유효하지 않은 경우(0 또는 `None`), `buy_order` API가 호출되지 않고 즉시 실패 응답을 반환하는지를 검증하는 `test_place_buy_order_limit_price_validation` 테스트 케이스를 추가했습니다.

## 5. 긴급 추가 수정 (2025-10-12)

최초 구현 완료 후 리뷰를 통해 다수의 치명적인 런타임 오류가 발견되어 긴급 수정 작업을 진행했습니다. 이 수정은 시스템이 실제 거래에서 동작 불능 상태에 빠지는 것을 방지하기 위해 필수적이었습니다.

### 5.1. 백엔드 긴급 수정 내역

#### `app/services/order_service.py` - 런타임 오류 수정
- **`AttributeError` 해결**: `APIResponse` 객체를 `dict`처럼 사용하거나(`api_response['output1']`), 존재하지 않는 `.get_message()` 메서드를 호출하던 부분을 모두 수정했습니다. 이제 `.get_body()`를 먼저 호출하여 API 응답 본문에 안전하게 접근합니다.
- **`ValidationError` 해결**:
    - `OrderDetail` 모델 생성 시, API 응답의 시간 문자열(`HHMMSS`)을 `datetime` 객체로 파싱하고, 누락되었던 모든 필수 필드(`order_amount`, `commission` 등)를 기본값으로 채워 Pydantic 검증 오류를 해결했습니다.
    - `PendingOrdersResponse`, `OrderHistoryResponse` 반환 시 `success`, `message` 등 필수 래퍼 필드를 포함하도록 수정했습니다.
- **주문 정정/취소 기능 임시 비활성화**: 정정/취소 주문에 필요한 `지점코드`, `원주문번호` 등의 파라미터를 현재 아키텍처에서 안정적으로 관리하기 어렵다고 판단했습니다. 런타임 오류를 방지하기 위해 해당 기능들을 임시 비활성화하고, "지원되지 않는 기능"임을 명시적으로 반환하도록 조치했습니다.

#### `app/core/korea_invest.py` - API 호출부 수정
- **실제 메서드명 사용**: `inquire_history` 등 존재하지 않는 메서드명 대신, 실제 `ki_api`에 구현된 `get_daily_ccld`, `revise_order` 등으로 호출 대상을 변경했습니다.
- **파라미터 업데이트**: `modify_order`, `cancel_order`의 시그니처를 실제 API가 요구하는 `branch_code`, `org_order_no` 등을 포함하도록 수정했습니다.

#### `tests/test_order_service.py` - 테스트 코드 수정
- `OrderRequest` 생성 시 누락되었던 `stock_name` 필드를 추가하여 `ValidationError`를 해결하고, 테스트가 정상적으로 실행될 수 있도록 수정했습니다.

### 5.2. 수정 후 결론

이번 긴급 수정을 통해, 최초 구현에 존재했던 심각한 런타임 오류들을 해결하여 **매수/매도 주문 및 내역 조회 기능이 안정적으로 동작**하도록 만들었습니다. 주문 정정/취소 기능은 안정성을 위해 임시 비활성화되었으며, 추후 아키텍처 보강 후 재구현이 필요합니다. 시스템은 이제 실제 매매에 투입될 수 있는 최소한의 안정성을 확보했습니다.

## 6. 리뷰 후 추가로 확인된 문제점과 보완 전략 (2025-10-12 18:00 갱신)

실 매매 투입 전 최종 점검 과정에서 다음과 같은 치명적인 결함이 다시 확인되었습니다. 9시간 후 예정된 실거래를 안전하게 진행하려면, 아래 항목을 **반드시 선행**해야 합니다.

### 6.1 미체결/체결 조회 API 연결 오류
- **문제**: `KoreaInvestAPIService.inquire_pending_orders`가 존재하지 않는 `get_unclosed_orders` 메서드를 호출하고 있습니다. 현재 `ki_api.py`에는 이 메서드가 없어 호출 즉시 `AttributeError`가 발생합니다.
- **대책**:
  1. `ki_api.py`에 한투 미체결 조회 TR(`inquire-time-orderbook` 혹은 `inquire-balance` 관련)의 래퍼를 신설하거나, 이미 구현된 함수(`get_daily_ccld`)를 재사용할 수 있도록 정확한 메서드를 파악합니다.  
  2. `KoreaInvestAPIService.inquire_pending_orders`에서 해당 메서드를 호출하도록 수정하고, 응답 형식을 명확히 정의합니다.  
  3. 응답 값(`output1`)이 없는 경우, 빈 리스트를 반환하도록 방어 로직을 넣습니다.

### 6.2 체결 내역 조회 데이터 타입 불일치
- **문제**: `KoreaInvestAPIService.inquire_order_history`는 `ki_api.get_daily_ccld`를 호출하는데, 이 함수는 `pandas.DataFrame`을 반환합니다. 현재 `OrderService.get_order_history`에서는 `APIResponse` 객체라고 가정하고 `.is_ok()`를 호출하여 `AttributeError`가 발생합니다.
- **대책**:
  1. `ki_api.get_daily_ccld`를 호출한 뒤 `DataFrame`을 그대로 받아오는 방식을 유지할지, 혹은 `APIResponse`를 반환하도록 `ki_api.py`를 수정할지 결정합니다.  
  2. 만약 `DataFrame`을 그대로 사용한다면 `OrderService`에서 `DataFrame`을 안전하게 순회하여 `OrderDetail`을 생성하는 전용 파서 함수를 만듭니다.  
  3. 파싱 중 예외가 발생하면 해당 행을 스킵하고 로깅하도록 하여 전체 조회가 실패하지 않게 합니다.

### 6.3 주문 응답 파싱 오류
- **문제**: 주문 응답 파싱 시 `APIResponse.get_body()`가 반환하는 객체가 dict가 아닌데도 dict 메서드를 사용하고 있습니다. 실제로는 `response.get_body().output`이 dict 형태이고, 오류 메시지는 `response.get_body().msg1` 등에 존재합니다.
- **대책**:
  1. `APIResponse`의 구조(`msg1`, `output`, `output2` 등)를 확인하고, 공용 헬퍼 함수를 만들어 `msg1`과 주문 번호(`ODNO`)를 안전하게 추출합니다.  
  2. 성공 시 `order_number`가 `None`이면 추후 취소/정정이 불가능하므로, 주문 응답에서 `ODNO`, `KRX_FWDG_ORD_ORGNO` 등을 반드시 저장하도록 요구합니다. 저장 위치(DB 혹은 메모리 캐시)를 확정합니다.  
  3. 실패 메시지는 `msg1`을 우선 사용하되, 없을 경우 `"알 수 없는 오류"`와 같은 기본값을 반환합니다.

### 6.4 `OrderDetail` 스키마 위반
- **문제**: `OrderDetail` 생성 시 `raw_data=item` 등 정의되지 않은 필드를 전달하고 있으며, `order_time`, `filled_time`에 `None`이 들어가면서 Pydantic 검증이 실패합니다.
- **대책**:
  1. `OrderDetail` 생성자는 정의된 필드만 채우도록 정리합니다. 원본 데이터를 보관하려면 별도 필드(ex: `extra: dict = Field(default_factory=dict)`)를 모델에 추가하거나, 서비스 레벨에서만 보관합니다.  
  2. 시간 문자열을 파싱할 때 실패하면 `datetime.now()` 등 안전한 기본값을 사용하고, 로그로 남겨 추적할 수 있게 합니다.  
  3. 금액/수수료 필드는 기본값 0으로 세팅하되, 실제로 제공되는 값이 있으면 정확히 반영합니다.

### 6.5 정정/취소 기능
- **현황**: 현재는 “지원되지 않습니다” 응답을 반환하지만, 나중에 기능을 복구하기 위한 최소 설계가 필요합니다.
- **대책**:
  1. 주문 성공 시 `order_number`, `branch_code`, `org_order_no` 등 KIS가 요구하는 키 정보를 저장할 위치(예: Redis/DB)를 미리 결정합니다.  
  2. 정정/취소 요청이 들어오면 저장된 정보를 가져와 API를 호출하는 플로우를 문서화하고, 테스트 케이스를 마련합니다.  
  3. 기능 복구 전까지는 프론트엔드에서도 정정/취소 버튼을 비활성화하거나 안내 문구를 띄워 사용자가 혼란스럽지 않도록 합니다.

## 7. 즉시 실행을 위한 작업 순서 (제안)
1. `ki_api.py`와 `KoreaInvestAPIService`를 먼저 정비하여 **모든 API가 존재하고 올바른 타입을 반환**하도록 맞춤.  
2. `OrderService`에서 **응답 파싱 헬퍼**를 도입해 주문/조회 공통 파싱을 통일.  
3. `OrderDetail` 및 `PendingOrdersResponse`/`OrderHistoryResponse` 생성 로직을 **스키마 일치**하도록 수정 후 단위 테스트 작성.  
4. `/api/orders/pending`, `/api/orders/history`에 대한 **샌드박스 통합 테스트** 수행(미체결 주문 넣은 후 재조회).  
5. 정정/취소 기능은 프론트 포함 명시적으로 비활성화 공지. 동시에 향후 복구를 위한 설계 메모를 별도 문서화.

위 계획을 문서와 코드에 반영하면서 진행 상황을 `docs/work-log/2025-10-12.frontend-error-resolution.md`에도 동기화해 주세요. 이렇게 해야 실거래 전 남은 시간이 9시간뿐인 긴박한 상황에서도 안정성을 확보할 수 있습니다.
